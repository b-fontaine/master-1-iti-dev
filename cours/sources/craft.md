# Software craftsmanship à l'ère des agents : où va la qualité du code ?

## TL;DR
- **Ta prémisse est confirmée par les données 2024-2026, mais elle doit être reformulée.** La quasi-totalité des mesures empiriques disponibles (GitClear, CodeScene, Stanford/Denisov-Blanch, DORA 2024, Cursor/CMU, Veracode, METR) convergent : l'IA sans discipline de qualité dégrade la maintenabilité, et cette dégradation est *plus forte* sur du code déjà malsain — exactement ton cas legacy .NET/WPF. Mais la formulation défendable devant un CTO n'est pas « on ne peut pas maintenir sans qualité élevée » ; c'est « la qualité du code (santé structurelle + tests) est devenue le facteur limitant de la performance des agents eux-mêmes ».
- **Le mouvement craft ne meurt pas, il se déplace.** Kent Beck (« augmented coding »), Sandro Mancuso (Codurance), Martin Fowler, Dave Farley disent tous une version de « la qualité compte plus, pas moins ». Mais Robert C. Martin (Uncle Bob) a opéré un revirement radical en juillet 2026 : il ne lit plus le code de ses agents et remplace la revue par un « gauntlet » de tests/métriques — signe que même le noyau craft se fracture sur *où* placer la qualité (revue humaine vs guardrails automatisés).
- **La thèse adverse (« le code devient jetable », Tessl/Podjarny, Karpathy « Software 3.0 ») est réelle et financée (125 M$), mais reste non démontrée en production sur des systèmes régulés/état persistant.** Aucune organisation documentée ne « régénère au lieu de maintenir » à grande échelle sur du B2B critique. Pour ton contexte, c'est un pari, pas une base de décision.

## Key Findings

1. **Le consensus empirique 2024-2026 est net et convergent** : plus d'AI-authored code sans garde-fous = plus de duplication, moins de refactoring, plus de churn, plus de defects, moins de stabilité de livraison. Les chiffres viennent de sources multiples et méthodologiquement indépendantes.
2. **La donnée la plus décisive pour toi** : les gains de l'IA s'effondrent sur brownfield complexe (Stanford : 0-10 %, parfois négatifs ; médian global 10-15 %) et le taux de casse des agents monte d'au moins 30 % sur code « unhealthy » (étude peer-reviewed CodeScene), voire davantage sur du vrai legacy. Ton legacy .NET/WPF mal testé est précisément le terrain où l'IA détruit le plus de valeur.
3. **Les pratiques craft qui survivent se renforcent** : TDD (comme guardrail des agents), tests d'architecture, small PRs, context engineering. Celles qui se transforment : code review (goulot d'étranglement), pair programming, lisibilité (« pour qui écrit-on ? »). Celle qui s'effondre mécaniquement : le refactoring manuel.
4. **Attention aux conflits d'intérêts** : GitClear, SonarSource, CodeScene, Veracode, Tessl, Codurance, Arolla vendent tous quelque chose sur ce sujet. Leurs données vont dans le sens de leur produit. Je les signale systématiquement ci-dessous. Les sources les plus neutres sont académiques (METR, Stanford, CMU/He et al.) et le rapport DORA.

## Details

### 1. Le mouvement craftsmanship face à l'IA (positions primaires datées)

**Kent Beck — la source la plus utile pour toi.** Dans « Augmented Coding: Beyond the Vibes » (Substack Tidy First?, 25 juin 2025), Beck distingue nettement le *vibe coding* (« you don't care about the code, just the behavior ») de l'*augmented coding* (« you care about the code, its complexity, the tests, & their coverage. The value system in augmented coding is similar to hand coding — tidy code that works. It's just that I don't type much of that code »). Point crucial : son système de prompt impose explicitement le cycle TDD Red→Green→Refactor et le principe Tidy First (séparer changements structurels et comportementaux). Beck a construit une bibliothèque B+Tree en Rust et Python en 4 semaines de cette façon, mais admet lui-même : « I feel good about the correctness & performance, not so good about the code quality... there's just too much accidental complexity. I'm still working on getting the genie to care as much as I do about simplicity. » Il surveille trois signaux d'alerte : boucles, fonctionnalités non demandées, et « triche » de l'agent (désactiver ou supprimer des tests). Sa formule médiatisée — 90 % de ses compétences dévaluées, 10 % multipliées par 1000 — traduit l'idée que le jugement de design, pas la frappe de code, est ce qui reste précieux.

**Robert C. Martin (Uncle Bob) — le revirement le plus spectaculaire.** En juillet 2026, dans un thread sur X, Martin a déclaré ne plus lire le code produit par ses agents, remplaçant la revue ligne-à-ligne par un dispositif de contraintes automatisées : unit tests, tests d'acceptation Gherkin, mutation testing, cyclomatic complexity, analyse de dépendances, coverage. Il redéfinit le rôle de l'ingénieur de « relecteur de code » vers « architecte de la qualité ». Cette position l'a mis en opposition directe avec Grady Booch, qui soutient que les métriques structurelles ne détectent pas les vulnérabilités ni le dead code qu'un ingénieur expérimenté repère à l'œil. Martin lui-même nuance (« just because we can do them doesn't mean we actually should » à propos de la surcharge de tests). À signaler : c'est un renversement du principe central de *Clean Code* (2008) selon lequel le code est écrit pour être lu par des humains. Fait notable : les principes de *Clean Code* connaissent une seconde vie comme « skills » / fichiers d'instructions (AGENTS.md, CLAUDE.md) pour cadrer les agents.

**Sandro Mancuso / Codurance — la position craft officielle la plus argumentée.** Article « Software Craftsmanship in the AI Era » (9 février 2026, mis à jour 1er juin 2026). Thèse centrale : « AI is the engine. Craftsmanship is the compass. » Arguments clés, tous directement applicables à ton cas :
- Le vrai goulot n'a jamais été la frappe : moins de 25 % du temps développeur est passé à éditer du code (citant Microsoft Research 2019) ; le reste est lecture/compréhension. L'IA n'enlève pas ce coût, « in many cases, it amplifies it ».
- L'IA **amplifie les défauts existants** : « A bloated class gets even bigger. A poorly named method is copied and modified elsewhere. » Craftsmanship devient donc « even more important, not less ».
- Crise des « massive pull requests » : les PR grossissent, les reviewers rubber-stampent, la qualité chute. Réponse craft : small commits, small PRs, revue réelle, pair programming.
- Perte de connaissance accélérée : un développeur en coaching Codurance ne pouvait pas expliquer sa propre PR (« I'm not sure. I'd have to look at the code again »). Le développeur devient « passive editor, not active author ».
- Sur le TDD : générer les tests *après* le code « flips testing on its head » — les tests deviennent un rubber-stamp qui cimente les bugs. À noter : Codurance a un intérêt commercial (offres « Data & AI Readiness Assessment », « AI in Engineering Assessment » ; devenu partenaire OpenAI et Anthropic en 2026) — c'est une source primaire crédible mais avec un produit à vendre.

**Martin Fowler (Thoughtworks).** Dans « Expert Generalists » (co-écrit avec Unmesh Joshi et Gitanjali Venkatraman) et ses interventions 2025 (podcast Pragmatic Engineer, 19 nov. 2025), Fowler soutient deux idées : (1) les LLM introduisent le **non-déterminisme** dans la programmation — un changement de nature, pas seulement de niveau d'abstraction (un prompt en version control ne garantit pas un comportement identique) ; (2) « refactoring is more important than ever » et l'output LLM doit être testé rigoureusement. Il valorise l'« expert generalist » qui maîtrise les fondamentaux pour évaluer et adapter les suggestions de l'IA. Il pointe aussi la « lethal trifecta » comme zone de danger.

**Dave Farley (Continuous Delivery).** Position constante 2024-2026 : « typing code was never the hard part of software engineering » (X, 18 août 2025, s'adressant explicitement aux CTO/Tech Leads sur le « seductive trap »). Il cite ~55 % de gain de productivité au mieux (pas 10x), et surtout un principe corroboré par DORA : « if you're already working well, AI will be a big win... But if you're working poorly, you're just going to dig a deeper hole faster. » Message pour un éditeur legacy : l'IA amplifie l'état existant de ta discipline d'ingénierie.

**La communauté française.** NewCrafts Paris (édition 2025, 6-7 novembre) affirme sur son site : « we believe craft is as important as ever, perhaps even more so » à l'ère des agents — tout en annonçant une **pause** (pas d'édition 2026, réévaluation pour 2027, difficultés financières + besoin de repenser le sens). Talk le plus centré : Thomas Coopman, « Human vs Machine » (live coding humains vs LLM vs « cyborgs »). Côté praticiens : **Arnaud Lemaire** (keynote « From Code to Consequences », AlpesCraft, 4 juillet 2025) : « L'ownership, la responsabilité, l'empathie : ça, c'est toujours à nous » et « AI is getting very good at writing code. But writing code was not where we were losing most of our time. » **Thomas Pierrain** (bio NewCrafts 2025) : le craft « paired with AI » vise à « augmenting people and organizations instead of replacing them ». **Cyrille Martraire** (Arolla) a publié la 2e édition de *Software Craft* (Dunod, 11 juin 2025) enrichie de deux chapitres sur l'IA et le DDD. **Arolla** s'est repositionné commercialement en « agentic software crafters » / « AI native engineering », avec cette formule de son CMO Arnaud Lacroix (publi-info Le Monde Informatique) : « sans encadrement ni configuration adéquate, le code généré accentuera forcément la dette technique de manière colossale... C'est un véritable cercle vicieux. » **Devoxx France 2025** a vu plusieurs talks « TDD + IA » (Manuel Camargo « Apprenez à votre IA à faire du TDD » ; « IA Générative, TDD et Architecture Hexagonale »), et 2026 est décrite comme « l'ère de l'agentique » avec des talks sur AGENTS.md et le context engineering pour imposer les standards d'architecture aux agents. Non trouvé : positions primaires datées de Xavier Detant et Jean-Laurent de Morlhon sur IA + qualité.

### 2. Les pratiques craft à l'épreuve des agents

**TDD — se renforce.** Convergence remarquable entre Beck, Mancuso, Willison, Uncle Bob et la communauté FR : le TDD devient le garde-fou (« guardrail ») des agents. Simon Willison documente le « red/green TDD » dans son guide « Agentic Engineering Patterns » (2026) : le test-first « helps agents write more succinct and reliable code with minimal extra prompting ». Le mécanisme : les tests contraignent le non-déterminisme de l'agent et détectent ses régressions. Nuance de Mancuso : le TDD assisté par IA n'a de valeur que si les tests précèdent (ou au moins encadrent) la génération ; sinon ils cimentent les défauts.

**Refactoring — s'effondre mécaniquement (donnée GitClear).** GitClear (⚠️ éditeur d'outils, vend de l'analyse de code) : le pourcentage de lignes « moved » (proxy du refactoring) est passé de ~24-25 % en 2021 à moins de 10 % en 2024 ; le rapport « The Maintainability Gap » (juin 2026, 623 millions de changements 2023-2026) chiffre le refactoring à −70 % vs baseline 2022, la maintenance legacy à −74 %, la duplication de blocs à +81 %, le copy/paste intra-commit à +41 %. 2024 est la première année où le copy/paste dépasse le code « moved ». **Critique méthodologique à porter devant ton CTO** : ces résultats sont *corrélationnels*, pas causaux (GitClear le reconnaît indirectement) ; « moved lines » mesure un comportement d'édition, pas directement la qualité ; et GitClear a un intérêt à documenter un problème que son produit résout.

**Clean Code / SOLID / DDD — deviennent du « contexte » pour l'agent.** Point de synthèse le plus important (voir section 5) : plusieurs sources convergent sur l'idée que du code propre = meilleur contexte = meilleurs outputs. Mancuso : « Well-modularised, well-named, and well-tested code doesn't just help humans navigate the system, it gives AI tools better patterns to work with. »

**Code review — devient le goulot d'étranglement principal.** C'est le point de bascule identifié par presque toutes les sources. Faros AI (2025) : l'adoption de l'IA coïncide avec un temps de revue des PR en hausse de 91 % et un bug rate +9 % par développeur, avec +98 % de PR mergées. Deux écoles se dessinent : (a) Mancuso — préserver la revue humaine via small PRs ; (b) Uncle Bob — abandonner la revue humaine au profit d'un gauntlet automatisé. Ta décision d'architecte consiste à choisir où tu places le curseur.

**Lisibilité — « pour qui écrit-on ? »** Débat ouvert et documenté. La maxime SICP (« programs must be written for people to read ») est explicitement questionnée par CodeScene : « textual source code now has a broader audience: machines need to understand it, too. » Position émergente : on écrit désormais pour les humains ET les agents, et il se trouve que les deux préfèrent le même code (sain, modulaire, testé).

### 3. Les données sur qualité et maintenabilité (le cœur)

**Stanford / Yegor Denisov-Blanch (Software Engineering Productivity Research Group, ~120 000 développeurs sur 600+ entreprises, source académique quasi-neutre).** LA donnée la plus importante pour un éditeur legacy. Le lift médian de productivité est de **10-15 %**, pas les 60 % du marketing (Denisov-Blanch, AI Engineer Code Summit 2025 : « The median productivity lift from AI tools is 10–15%. Not 60%. Not even close »). Décomposition par type de tâche : greenfield simple 30-40 % ; greenfield complexe 10-15 % ; **brownfield simple 15-20 % ; brownfield complexe 0-10 %, parfois négatif**. Environ la moitié des gains bruts est mangée par le *rework* (correction de bugs, hallucinations, non-respect des conventions). Mécanisme : les LLM manquent de contexte sur les dépendances du code legacy. Écart de perception majeur : les développeurs surestiment largement leur propre gain.

**CodeScene / Adam Tornhill (⚠️ éditeur, vend l'analyse « Code Health »).** Distinction importante à faire devant ton CTO entre l'étude peer-reviewed et le whitepaper produit :
- **Étude peer-reviewed** « Code for Machines, Not Just Humans: Quantifying AI-Friendliness with Code Health Metrics » (Markus Borg & Adam Tornhill ; 5000 programmes, 6 LLM ; communiqué PRNewswire du 28 janvier 2026) : « AI-coding assistants increase defect risk by at least 30 percent when applied to unhealthy code, with real-world risk likely far higher in legacy systems. » C'est le chiffre solide : **+30 % minimum**.
- **Whitepaper produit** « AI-Ready Code: How Code Health Determines AI Performance » (7 janvier 2026, v2 5 mars 2026) : avance +60 % — mais ce chiffre vient du matériel commercial, pas de l'étude peer-reviewed ; à ne pas citer comme s'il était revu par les pairs.
- Point crucial : l'étude n'a testé que du code avec Code Health ≥ 7.0, donc « reality is worse. Much worse » sur du legacy scoré 3-4 (projection non-linéaire). Chez loveholidays (cas client cité) : Claude en agentique a d'abord dégradé la code health, puis après safeguards « code health-aware » l'équipe est passée de 0 à 50 % de code assisté par agent en 5 mois. Citation clé (Stuart Caborn, Distinguished Engineer, loveholidays) : « AI has an amplifying effect. If your engineering practices are strong, AI helps you move faster. If they're weak, it will destroy you. » CodeScene affirme aussi que les agents consomment 35-50 % de tokens en plus sur du code unhealthy.

**DORA 2024 (Google, ~3 000 répondants, source relativement neutre).** Pour chaque hausse de 25 % de l'adoption de l'IA : stabilité de livraison **−7.2 %**, throughput **−1.5 %** — alors qu'au niveau individuel l'IA apporte +2.1 % de productivité et +2.6 % de flow. Le suivi 2025 montre le throughput repassé positif mais la stabilité toujours dégradée. Mécanisme : PR plus grosses, moins modulaires, plus difficiles à intégrer. Message DORA : l'IA « accélère le développement et expose les faiblesses du système environnant ».

**Cursor / CMU (He et al., « Speed at the Cost of Quality », MSR 2026 — académique, design causal).** Étude quasi-expérimentale (difference-in-differences) sur 806 repos GitHub ayant adopté Cursor (janvier 2024-mars 2025). Résultat : hausse de vélocité « large mais transitoire », et hausse « substantielle et persistante » des static analysis warnings et de la complexité du code — cette dégradation étant elle-même le facteur causal du ralentissement de vélocité à long terme. C'est la meilleure preuve causale (pas seulement corrélationnelle) que l'IA sans QA dégrade durablement.

**METR (juillet 2025, RCT — le plus rigoureux méthodologiquement).** Essai contrôlé randomisé (Becker, Rush, Barnes, Rein ; 16 développeurs open-source expérimentés, 246 tâches, sur leurs propres repos, avec Cursor Pro + Claude 3.5/3.7) : « when developers use AI tools, they take 19% longer than without—AI makes them slower » (IC +2 % à +39 %), alors qu'ils s'estimaient 20 % plus rapides. À nuancer honnêtement : petit échantillon, modèles début 2025, et METR a annoncé (24 février 2026) revoir son design car les développeurs refusaient de travailler sans IA (le sous-échantillon re-testé montrait −18 %) — signe que la valeur perçue est réelle et dépend du contexte.

**Sécurité — Veracode (⚠️ éditeur sécurité).** « 2025 GenAI Code Security Report » (>100 LLM, 80 tâches, Java/Python/C#/JS) : 45 % du code généré introduit une vulnérabilité OWASP Top 10 ; Java 72 % de taux d'échec ; XSS (CWE-80) 86 % d'échec, log injection (CWE-117) 88 %. Jens Wessling, CTO : « Our research reveals GenAI models make the wrong choices nearly half the time, and it's not improving. » Mise à jour « Spring 2026 » : le taux de réussite sécurité stagne à ~55 % « virtually identical to where they stood two years ago » malgré >95 % de correction syntaxique. Apiiro (Fortune 50) : +322 % de chemins d'escalade de privilèges, +153 % de design flaws. Point non-résolu : les métriques structurelles ne détectent pas les vulnérabilités (l'argument de Grady Booch contre Uncle Bob).

**Études académiques (code smells).** « Investigating The Smells of LLM Generated Code » (Paul, Zhu & Bayley, arXiv 2510.03029, oct. 2025) : le code généré par LLM a « a higher incidence of code smells compared to reference solutions » et « noticeably poorer » que le code humain, la complexité augmentant davantage sur les tâches complexes. « AI-Generated Smells » (arXiv 2605.02741, PyExamine) documente aussi des smells architecturaux (Scattered Functionality, Unstable Dependencies).

**Les contre-données (à documenter honnêtement).** Existe-t-il des preuves que le code IA est égal ou supérieur ? Nuances réelles : (1) sur greenfield simple, les gains sont réels (30-40 %, Stanford) ; (2) syntaxiquement, le code IA est >95 % correct (Veracode) ; (3) l'adoption est massive — 2025 Stack Overflow Developer Survey (49 009 réponses, 29 mai-23 juin 2025) : **84 % des devs utilisent ou prévoient d'utiliser l'IA** (vs 76 % en 2024) — et METR montre que les devs refusent de revenir en arrière. **Mais attention à la nuance de confiance** : dans cette même enquête, seuls 29 % font confiance à l'exactitude du code IA (vs 40 % l'année précédente), 46 % s'en méfient activement, et 66 % citent des réponses « almost right, but not quite ». La valeur perçue est réelle mais la confiance *baisse*. (4) Cui et al. (essai multi-entreprises, 4867 devs Microsoft/Accenture/Fortune 100) : gain moyen 26 %, mais concentré sur les juniors ; les seniors familiers de leur codebase ne montrent quasi aucun gain mesurable. **Aucune étude longitudinale sur 2-3 ans de maintenabilité de codebases à forte proportion d'IA n'existe encore** — c'est un angle mort que tu dois signaler à ton CTO : on extrapole des tendances de 2-4 ans, pas des cycles de vie complets.

### 4. La thèse adverse — « le code devient jetable »

**Qui la porte.** Tessl (Guy Podjarny, fondateur de Snyk) est le porte-étendard, financé à hauteur de 125 M$ (25 M$ seed via boldstart + GV, puis 100 M$ Série A menée par Index Ventures avec Accel/GV, annoncé le 14 novembre 2024, valorisation post-money ~750 M$). Thèse : passer du « code-centric » au « spec-centric » — la spec devient la source de vérité, le code devient un artefact régénérable et jetable. Citation Podjarny : « code will become disposable and that implementations will be something that is just kind of created ». Vision : apps « language-agnostic », régénérables de JavaScript vers Python, iPhone vers Android, à partir de la même spec, avec des tests dérivés de la spec pour garantir la non-régression. Andrej Karpathy (« Software 3.0 ») fournit le cadre intellectuel plus large.

**Les limites documentées de cette thèse.** À porter devant ton CTO :
- **Non-déterminisme** (Fowler) : régénérer ne produit pas le même résultat ; sur un système à état persistant, contrats d'API stables, ou données migrées, c'est disqualifiant.
- **La spec devient le nouveau code legacy** : une spec suffisamment précise pour être régénérable de façon fiable tend vers la complexité du code qu'elle remplace. Tessl reconnaît que « specs are intentionally incomplete ».
- **Coût de re-vérification** : chaque régénération exige une re-validation complète (sécurité, conformité, performance) — prohibitif en environnement régulé.
- **État de maturité** : au moment de l'annonce (Fortune, nov. 2024), Tessl « is not yet ready... to begin selling the software to paying customers » et testait des versions préliminaires. **Aucune organisation documentée ne régénère plutôt que ne maintient à grande échelle sur du B2B critique.** C'est une vision d'investisseur, pas une pratique établie.

**Verdict sur la thèse adverse** : intellectuellement sérieuse, mais pour un éditeur B2B multi-BU avec legacy .NET/WPF et état persistant, c'est un pari non prouvé. Le « code jetable » fonctionne aujourd'hui pour du prototype/greenfield throwaway, pas pour tes systèmes de production.

### 5. La synthèse émergente — qualité pour qui et pourquoi

C'est ici que se trouve la réponse la plus défendable à ta question. La thèse « la qualité compte *plus*, pas moins » repose sur un mécanisme précis : **l'agent lit le code comme contexte, donc un code sain est un meilleur contexte, qui produit de meilleurs outputs.**

Preuves convergentes :
- **CodeScene** : +30 % de defect risk minimum sur code unhealthy (peer-reviewed), développement plus rapide en code sain, tokens consommés 35-50 % en plus sur code unhealthy. « Code Health gives AI that ground truth. »
- **Stanford** : gains négatifs sur brownfield complexe = preuve *indirecte* que l'architecture existante est le facteur limitant.
- **Mancuso** : le code propre « gives AI tools better patterns to work with ».
- **Patterns émergents « AI-readable / agent-friendly »** : fichiers AGENTS.md / CLAUDE.md pour encoder les standards ; « context engineering » ; MCP servers « code-health-aware » ; Clean Code réincarné en « skills ».

**Où se déplace la responsabilité qualité** : des humains-qui-tapent-du-code vers un système de garde-fous — tests (surtout d'acceptation et d'architecture), specs, evals, quality gates automatisés, et santé structurelle de la codebase comme actif de premier ordre. La revue humaine se concentre là où les métriques sont aveugles (sécurité, intention métier, dead code).

### 6. Implications pratiques pour ton éditeur B2B avec legacy .NET/WPF

**Le risque spécifique #1** : accélérer la production de code sur une base déjà dégradée. Toutes les données (DORA, CodeScene, Farley, Stanford) disent la même chose — l'IA sur du legacy mal testé « will destroy you » plus vite. Ton legacy .NET/WPF mal testé est le pire terrain de départ.

## Recommendations

**Étape 0 — Mesurer avant d'accélérer (0-1 mois).** Établis une baseline objective *avant* de déployer les agents largement. Instrumente : code health / hotspots (le legacy .NET/WPF concentrera le risque), test coverage réel, DORA metrics (change failure rate + rework/churn en priorité, pas la vélocité). Sans baseline, tu ne pourras pas prouver l'impact à ton CIO. Seuil de décision : identifie les modules à Code Health < 7 (ou équivalent complexité cyclomatique/duplication) — ce sont les zones où tu interdis l'agentique autonome.

**Étape 1 — Zonage brownfield/greenfield (1-3 mois).** Applique la matrice Stanford : autorise l'agentique large sur greenfield/modules simples (gains 30-40 %) ; sur le legacy complexe, l'agent reste en mode « augmented » (Beck) sous supervision serrée, jamais en autonomie. Benchmark de bascule : si le rework rate d'un module dépasse ~50 % des gains bruts, retire l'agentique de ce module.

**Étape 2 — Guardrails avant volume (2-4 mois).** Mets en place les quality gates qui rendent la qualité « inévitable » (approche Uncle Bob, mais en gardant la revue humaine sur la sécurité et l'intention métier — contra Uncle Bob, pro Booch/Veracode, car les métriques structurelles ne détectent pas les vulnérabilités) :
- CI/CD bloquant : static analysis (SonarQube — ⚠️ éditeur), coverage, mutation testing, scan sécurité (SAST/SCA — Veracode montre 45 % de vulnérabilités), détection de duplication.
- TDD / tests d'architecture au niveau du prompt : encode tes standards dans des fichiers AGENTS.md/instructions (pattern Devoxx FR 2026, Codex/Beck).
- Politique de PR : impose des small PRs. C'est ton principal levier contre le goulot de revue (Faros : +91 % de temps de revue).

**Étape 3 — Traiter la santé du code comme un prérequis, pas un nice-to-have (3-12 mois).** Avant d'industrialiser l'agentique sur le legacy, uplift les hotspots les plus risqués (le pattern loveholidays : safeguards code-health-aware → passage à 50 % de code agent en 5 mois). Utilise l'IA elle-même pour le refactoring encadré par tests (contre-mesure directe à l'effondrement du refactoring documenté par GitClear).

**Étape 4 — Gouvernance de la connaissance (continu).** Contre la « perte de connaissance accélérée » (Mancuso) : impose que tout auteur de PR puisse expliquer sa PR ; garde le pair/mob programming sur les décisions de design ; documente les décisions d'architecture (specs comme complément, pas comme source de vérité unique — n'adopte pas la thèse Tessl en production).

**Ce qui changerait ces recommandations** : (a) si une étude longitudinale 2-3 ans montrait une maintenabilité stable sur codebases à forte proportion d'IA (n'existe pas encore) ; (b) si le non-déterminisme de la régénération était résolu (spec→code déterministe) — alors la thèse « code jetable » deviendrait défendable sur certains périmètres ; (c) si les taux de vulnérabilité du code IA chutaient nettement (Veracode montre une stagnation à ~55 % sur 2 ans — donc ne parie pas dessus).

## Conclusion : ta prémisse est-elle confirmée ?

**Confirmée, mais à reformuler pour être imbattable devant un CTO/CIO.** La version naïve (« on ne peut pas maintenir du code IA dans le temps sans qualité élevée ») est vraie mais attaquable : un contradicteur te répondra « et le code jetable, alors ? ». La version blindée par les données est : **la qualité du code n'est plus seulement une propriété souhaitable du produit fini, elle est devenue le facteur limitant de la performance des agents eux-mêmes.** Un code sain rend l'IA plus rapide, plus sûre, moins coûteuse en rework et en tokens ; un code malsain fait de l'IA un générateur de legacy accéléré. Sur ton terrain précis — legacy .NET/WPF mal testé, brownfield complexe, B2B multi-BU — c'est exactement le pire cas de départ (Stanford 0-10 %, CodeScene +30 % de defect risk minimum, DORA −7.2 % de stabilité). La thèse adverse du « code jetable » n'est pas de la science-fiction, mais elle n'est démontrée nulle part en production sur des systèmes critiques à état persistant. Ta conclusion défendable : investir dans la santé du code et les guardrails n'est pas de la nostalgie craft, c'est la condition économique pour que l'IA tienne ses promesses chez toi.

## Caveats
- **Conflits d'intérêts systématiques** : GitClear, CodeScene/Tornhill, SonarSource, Veracode, Tessl, Codurance, Arolla vendent tous un produit ou service lié à ce sujet. Leurs données penchent vers le problème que leur offre résout. Les sources les plus neutres : METR (RCT, à but non lucratif), Stanford/Denisov-Blanch (académique), CMU/He et al. (académique, causal), DORA (Google, mais méthodologie publique).
- **Distinction peer-reviewed vs marketing** : pour CodeScene, cite le +30 % de l'étude peer-reviewed (Borg & Tornhill), pas le +60 % du whitepaper produit.
- **Corrélation ≠ causalité** : GitClear et DORA sont corrélationnels. Seuls CMU/Cursor (difference-in-differences) et METR (RCT) établissent une causalité, et sur des périmètres limités.
- **Angle mort majeur** : aucune donnée longitudinale sur 2-3 ans de maintenabilité de codebases à forte proportion d'IA. Toutes les conclusions extrapolent des tendances courtes (2020-2026).
- **Recency** : les modèles évoluent vite ; METR (modèles début 2025) et certaines études peuvent sous-estimer les capacités des modèles fin 2025/2026.
- **Non trouvé** : positions primaires datées de Xavier Detant et Jean-Laurent de Morlhon sur IA + qualité ; programme horaire complet NewCrafts 2025 ; citation verbatim isolée de Cyrille Martraire (son positionnement passe par le livre 2025 et Arolla).
