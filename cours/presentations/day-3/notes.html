01 · Travailler à plusieurs · bloc 2

Titre de partie : travailler à plusieurs

0,5 min

À dire

Mercredi, vous avez appris git seul ou en binôme, dans un dépôt d'essai. Aujourd'hui, quatre ou cinq personnes et autant d'agents écrivent dans le même dépôt : il faut des habitudes communes.

Git en équipe : quatre habitudes

5 min, démonstration comprise
Petites PR · branches courtes · une relecture par les preuves · le conflit est normal · démonstration d'un conflit

À dire

Une petite PR annonce une seule chose : elle se démontre et se vérifie vite ; une grosse ne se vérifie plus, elle se survole. Une branche qui reste courte s'écarte peu de main et entre rarement en conflit. Relire, c'est vérifier par les preuves, avec une checklist : lire ce que la PR annonce, la voir fonctionner, vérifier que la liste des fichiers touchés correspond à l'annonce ; pas juger le code ligne à ligne. Et commenter précisément. Et quand le conflit arrive, ce n'est ni une erreur ni une faute : deux personnes ont touché le même endroit, git vous demande de choisir.

Démonstration courte, en direct : deux branches qui modifient le même fichier, la fusion de la seconde déclenche le conflit, on le résout.

À savoir

  • Le conflit pas à pas a été fait mercredi (séance 2, chapitre 1, section 7) : ne pas le refaire, le montrer dans un dépôt d'équipe dont main est protégée, donc via deux PR (chapitre 1 de la séance 3).
  • Préparer la démonstration à froid dans un dépôt jetable, pour ne pas dépendre du réseau.
  • Le bloc 2 est Important, pas Indispensable : s'il faut gagner du temps, réduire la démonstration, pas l'annonce des paires.

Question à poser

« Qui a déjà eu un conflit depuis mercredi ? Qu'avez-vous fait ? »

La règle de l'auteur : Simon Willison

1 min
« Don't file pull requests with code you haven't reviewed yourself » · traduction · l'avoir vue fonctionner, savoir l'expliquer · « c'est l'agent qui l'a écrit » n'est pas une réponse recevable

À dire

Avant la relecture par un autre, il y a la vôtre. Avant de demander la relecture, vous avez vu votre PR fonctionner et vous savez l'expliquer ; sinon, vous faites faire votre travail au relecteur. Avec un agent, c'est d'autant plus tentant : il produit vite, beaucoup, et proprement en apparence. Vous êtes l'auteur de ce que vous proposez.

À savoir

Citation telle qu'au programme (bloc 2). La page source n'a pas été relue pour ce diaporama : ne pas lui attribuer davantage à l'oral. Elle était donnée en lecture à la fin de la séance 2.

8 équipes : 01–04, 02–05, 03–06, 07–08 · 7 équipes : 02–05, 03–06, trio circulaire 01–04–07 (07 relit 01, 01 relit 04, 04 relit 07)

Les numéros attribués mercredi servent maintenant. Chaque équipe relira au moins une PR de l'équipe jumelée, plus tard dans la matinée. Annoncer la configuration de la promotion (8 ou 7 équipes) et laisser l'autre ligne de côté.

02 · La première user story · bloc 3

Titre de partie : la première user story

0,5 min

À dire

Le cœur de la matinée. Dix minutes de démonstration, puis chacun travaille avec son agent, sur sa branche.

De la story au code

10 min, démonstration
Plan → scénario .feature → tests unitaires (rouge) → code (vert, nettoyage) → PR · scénario du thème B (disponibilité) · use case, repository fake, Cubit

À dire

L'ordre compte. D'abord un plan, en mode plan, que vous critiquez. Puis le scénario en français, celui qu'un non-développeur peut lire : ici l'exemple du thème B, la disponibilité d'un quart de 480 minutes avec une pause de 30, une panne de 45 et un changement de série de 15. Le temps requis est de 450 minutes, le temps de marche de 390, la disponibilité de 86,7 %. Puis les tests unitaires, qui échouent ; puis le code qui les fait passer ; puis le nettoyage. Enfin la PR.

Le code se range dans les couches du squelette : le use case dans le domain, un repository « fake » qui stocke en mémoire derrière l'interface du domain, un Cubit testé avec bloc_test. Pas de base de données à ce stade, et l'écran peut attendre.

À savoir

  • Démonstration du programme, avant l'atelier : lancer le .feature d'exemple du squelette, montrer le test généré et le test du BLoC d'exemple.
  • Pour une sous-règle de domaine, les steps appellent directement le use case sans monter d'écran (vérifié avec bdd_widget_test 3.1.0 sur une copie du dépôt-modèle : chapitre 2, section 7).
  • Les valeurs du scénario sont entre accolades ({480}, {'pause'}) : sans elles, l'outil fond la valeur dans le nom de l'étape et fabrique une étape par valeur (chapitre 2, section 4). Les scénarios de l'énoncé des thèmes sont écrits ainsi.
  • Première ligne # language: fr obligatoire ; dart run build_runner build --delete-conflicting-outputs génère le test widget.
  • Sous-règles des autres thèmes (cours/projets/themes.md) : A, le total (règle 3) ; C, la priorité par rang (règle 2). Chacune est dans le PROJET.md de l'équipe.

Repérer un test « triché »

2 min
Test supprimé · désactivé · assoupli · scénario retouché · hasard en dur

À dire

Un agent à qui l'on demande « fais passer les tests » peut y arriver en changeant les tests. Cinq formes à reconnaître : un test supprimé, un test désactivé, une attente assouplie, un scénario retouché, ou une valeur aléatoire figée pour que le résultat tombe juste. Le réflexe : dans la liste des fichiers touchés de la PR, regarder d'abord si un test ou un scénario a bougé.

Question à poser

« Si l'agent remplace "86,7 %" par "87 %" dans le scénario, qu'est-ce qui a changé : le code ou la règle ? »

À savoir

Le programme cite « test ou scénario supprimé, désactivé, assoupli, hasard en dur ». C'est l'intention du bloc 3 : vivre le TDD avec un agent et apprendre à repérer un test triché.

03 · Le RGPD appliqué · blocs 4 à 7

Titre de partie : le RGPD appliqué à votre projet

0,5 min

À dire

On s'arrête de coder un moment. Avant de créer des tables, il faut savoir ce qu'on va y mettre et si c'est une donnée personnelle.

Le RGPD en une page

8 min
Donnée personnelle (art. 4) · principes (art. 5) · base légale (art. 6) · sous-traitants et transferts (art. 28, chapitre V) · violation, 72 h (art. 33) · un outil temporaire n'échappe pas au RGPD

À dire

Le RGPD, règlement (UE) 2016/679, s'applique depuis le 25 mai 2018. Une donnée personnelle, c'est toute information sur une personne identifiée ou identifiable, y compris par un pseudonyme qu'on peut lever. Trois principes nous servent tout de suite : une finalité précise, ne collecter que le nécessaire, fixer une durée de conservation. Il faut une base légale par finalité.

Le point qui vous concerne chaque jour : le fournisseur du modèle d'IA reçoit tout ce qui est dans un prompt. Écrire un prompt, c'est transmettre à un tiers. En cas de fuite, la notification à l'autorité se fait dans les 72 heures. Et un outil temporaire n'échappe pas au RGPD : dès qu'une donnée réelle y entre, tout s'applique, même pour une semaine.

À savoir

  • Source : cours/conformite-ai-act-rgpd.md, sections 2, 4 et 5. Ne rien affirmer qui n'y soit pas.
  • Le fournisseur du modèle est, selon le cas, sous-traitant ou destinataire : c'est au DPO de le qualifier (module, section 2).
  • Un secret commité dans un dépôt public est un incident à signaler au RSSI immédiatement.

Question à poser

« Un pseudonyme dans une base, est-ce encore une donnée personnelle ? »

Vos droits de citoyen européen

6 min
Information, accès, rectification, effacement, limitation, portabilité, opposition, pas de décision uniquement automatisée · réponse sous un mois · réclamation à la CNIL

À dire

Ces droits sont les vôtres, pas seulement ceux des utilisateurs de vos applications. Vous pouvez demander à un service quelles données il a sur vous, les faire corriger, effacer, geler, récupérer, vous opposer à leur usage, et refuser qu'une décision importante vous concernant soit prise par une machine seule. Le service doit répondre sous un mois, délai prolongeable. Sans réponse, ou en cas de refus injustifié, on saisit la CNIL.

À savoir

  • Articles : 13 et 14 (information), 15 (accès), 16 (rectification), 17 (effacement, pas absolu), 18 (limitation), 20 (portabilité), 21 (opposition), 22 (décision automatisée), 77 (réclamation), 12 (délai : un mois, prolongeable de deux mois).
  • C'est l'un des deux buts du module de conformité : que chacun sache exercer ses droits. Le bloc est Indispensable.
  • L'exercice de courriel de demande d'accès (module, section 5) est Moins utile en séance : le laisser en lecture ou le donner en tâche facultative avant la séance 4.

Question à poser

« Quel service, que vous utilisez tous les jours, aimeriez-vous interroger sur ce qu'il sait de vous ? »

Le test en 4 questions

4 min
Personnes réelles ? Décider pour quelqu'un ? Sortie vers un tiers ? Usage hors de l'équipe ? · données par thème : A, B, C · un seul « oui » : fiche et RSSI

À dire

Quatre questions, à appliquer à votre propre thème, dans l'atelier qui suit. Un seul « oui » suffit pour qu'il faille une fiche de conformité et un passage devant le RSSI. Rappel : vos données sont fictives ; la fiche raisonne sur ce qui se passerait en usage réel.

À savoir

  • Qualification par thème, telle qu'au programme : A, l'identifiant de l'utilisateur qui possède une fiche de passeur (un compte pseudonymisé reste personnel) ; B, postes et quarts, sans identifiant d'opérateur ; C, des étudiants et une décision d'affectation.
  • Le thème C demande plus de travail : décision qui touche des étudiants, question de l'art. 22. Passer d'abord dans ces équipes.
  • Le thème B n'est pas « sans risque » pour autant : les données de poste sont confidentielles pour l'entreprise (module, section 7).

Atelier · Test en 4 questions et début de la fiche

atelier
Quatre étapes : 4 questions, qualification, rubriques 1 à 5, PR relue · aucun nom civil ni courriel · fiche J

À dire

En équipe, sous la conduite du gardien produit et conformité. Répondez aux quatre questions pour votre thème, qualifiez vos données, puis remplissez les cinq premières rubriques de docs/fiche_conformite.md : finalité, données, personnes concernées, base légale ou justification « données fictives », durée de conservation et date de suppression. La fiche passe par une PR relue par un coéquipier.

À savoir

  • Le gabarit compte 13 rubriques (module, section 6.1) ; seules les rubriques 1 à 5 sont demandées aujourd'hui. Les rubriques 6 et 7 glissent entre S3 et S4.
  • Aucun nom civil ni courriel dans la fiche : « équipe n° X » et identifiants GitHub.
  • Sensibilisation, pas avis juridique : la validation revient au RSSI et au DPO.

Pièges

  • « Données fictives » écrit sans justification : la definition of done exige la justification.
  • Une durée de conservation sans date de suppression.
04 · Les données · blocs 8 et 9

Titre de partie : les données

0,5 min

À dire

Le code se réécrit ; les données, elles, restent. C'est pourquoi on les modélise avec soin et on ne les change que par des migrations.

Les données survivent au code

6 min
Modéliser (entités, relations, clés, contraintes) · drift (tables en Dart, code généré) · migrations versionnées (schemaVersion, onUpgrade) · jamais de modification à la main

À dire

Une entité, c'est une chose que l'on enregistre : un poste, un quart, un arrêt. Une relation les relie : un arrêt appartient à un quart. La clé primaire identifie chaque ligne ; la clé étrangère pointe vers une ligne d'une autre table ; les contraintes refusent ce qui n'a pas de sens.

drift, en une phrase : on déclare les tables en Dart, build_runner génère le code d'accès typé, sur SQLite. Chaque changement de schéma est une migration versionnée : un numéro, schemaVersion, et une stratégie, onUpgrade. On ne modifie jamais une base à la main : sinon personne ne peut rejouer le changement.

À savoir

  • Démonstration du programme : l'agent ajoute une table avec une migration et un test. La préparer à froid.
  • Le programme demande de vérifier MigrationStrategy et onUpgrade sur la version de drift utilisée : voir chapitre 4 des supports.
  • Les exemples d'entités ci-dessus sont ceux du thème B ; chaque équipe a les siennes dans PROJET.md.

Deux pièges, une règle

3 min
Piège 1 : l'agent corrige un test en modifiant les données · piège 2 : deux branches incrémentent schemaVersion · règle : une seule migration à la fois, coordonnée par le gardien des données

À dire

Premier piège : un test échoue, et l'agent le fait passer en changeant les données plutôt que le code. C'est la triche de tout à l'heure, du côté des données. Second piège : deux branches ajoutent chacune une migration et passent chacune schemaVersion au même numéro ; elles entrent en conflit. D'où la règle, que vous ajoutez à CLAUDE.md aujourd'hui : une seule migration à la fois, coordonnée par le gardien des données.

À savoir

Si deux branches ont malgré tout chacune leur migration, l'une est fusionnée, l'autre se met à jour depuis main et renumérote la sienne : le détail est au chapitre 4 des supports.

Question à poser

« Dans votre équipe, qui est le gardien des données ? Levez la main. »

Atelier · Modéliser et implémenter

atelier
Cinq étapes : modèle papier validé, tables drift, première migration, test d'intégrité, PR et fiche · fini quand : migrations rejouées, orpheline rejetée · fiche K

À dire

D'abord le papier : entités, relations, contraintes, et vous me le montrez avant de toucher au code. Ensuite, avec l'agent : les tables du thème dans la couche data, la première migration, et un test sur une base en mémoire qui prouve qu'on ne peut pas insérer une ligne orpheline, par exemple un arrêt qui pointe vers un quart inexistant. Le tout passe par une PR relue. Notez en commentaire dans la fiche de conformité les rubriques qui touchent aux données.

À savoir

  • Avec SQLite, les clés étrangères doivent être activées explicitement (le programme demande de le vérifier avec drift) : sans cela, le test d'intégrité passe pour de mauvaises raisons. Voir chapitre 4.
  • Le seed complet et la garde RequireRole (couche domain, avec test de refus) ne sont pas demandés en séance 3 : ils glissent.
  • Valider vite les modèles papier : c'est le goulet d'étranglement de l'atelier.

Pièges

  • Le test d'intégrité passe sans que les clés étrangères soient actives : vérifier qu'il échoue quand on les désactive.
  • Deux membres de l'équipe écrivent chacun une migration.
Revue croisée et bilan · blocs 10 et 11

Atelier · Revue croisée entre équipes

atelier
Quatre étapes : une PR de l'équipe jumelée, l'auteur explique, relire et commenter, un coéquipier approuve · fiches L et I

À dire

Chaque équipe relit au moins une PR de son équipe jumelée, par des commentaires sur GitHub, auteur présent : l'auteur explique sa PR à voix haute. L'approbation qui débloque la fusion vient d'un coéquipier de l'auteur, pas de l'équipe jumelée.

À savoir

  • Les équipes jumelées n'ont pas d'accès en écriture au dépôt de l'autre : le programme note cette variante « à vérifier ». Vérifier avant la séance qu'un compte sans droit d'écriture peut bien commenter une PR du dépôt public.
  • Le bloc peut commencer dès que des PR sont ouvertes : inutile d'attendre la fin des autres ateliers.
  • La definition of done demande aussi que chaque étudiant ait ouvert une PR et relu celle d'un autre.

Pièges

  • « LGTM » sans vérification : demander au relecteur ce qu'il a vérifié (scénario, tests verts, liste des fichiers).
  • Un commentaire vague (« c'est bizarre ») : demander une ligne et une proposition.

Livrable de fin de séance et definition of done

3 min
Première règle verte, modèle et migrations fusionnés, début de la fiche commité · quatre critères · fiche M

À dire

Le livrable est le même pour les trois thèmes. En détail : la première user story livrée (scénario .feature, tests, code, PR relue) ; le modèle de données (schéma, première migration, test d'intégrité) ; la fiche de conformité commitée avec ses rubriques 1 à 5 ; au moins une PR relue par une autre équipe. Vérifiez-le avec la fiche M avant de partir.

À savoir

Definition of done du programme : sur une base en mémoire vide, le schéma se crée et les migrations se rejouent sans erreur (test), une seule migration à la fois, flutter test vert ; un test prouve qu'une insertion orpheline est rejetée ; chaque étudiant a ouvert une PR (même petite) et relu celle d'un autre ; aucune donnée personnelle réelle dans le dépôt, la fiche existe et indique « données fictives » avec une justification, sans nom civil ni courriel ; la fiche est commitée (rubriques 1 à 5) et relue par un coéquipier. Le seed complet est attendu entre S3 et S4, au début de S4 ou au sprint.

Consignes de fin

3 min
