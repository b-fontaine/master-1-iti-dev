Exercice éclair : la règle d'or

3 min
« Qu'est-ce qu'on ne met jamais dans un prompt ? » · six réponses qui apparaissent

Question à poser

Poser la question avant de faire apparaître les réponses (la slide les révèle seule : rester sur le titre en posant la question, ou passer en vue d'ensemble). Faire répondre trois ou quatre personnes, puis compléter.

À dire

La règle d'or : aucune donnée personnelle ni confidentielle dans un prompt ni dans un dépôt public. Pourquoi ? Ce que vous écrivez dans un prompt part chez un tiers ; ce que vous poussez dans vos dépôts est publié, vos dépôts sont publics. Aujourd'hui, vous allez pour la première fois configurer un outil pour qu'il vous aide à tenir cette règle.

À savoir

Piège fréquent : « un fichier de stage » ou « un export de l'entreprise » ne ressemble pas à une donnée personnelle, et en contient presque toujours. Données fictives uniquement, y compris « juste pour tester ».

Constitution des équipes et attribution des thèmes

15 min
Cinq étapes : équipe, formulaire, trois équipes au plus par thème, numéro, rôles · les trois gardiens (plus conformité à 4, démonstration à 5)

À dire

Il n'y a pas eu de formulaire après la séance 1 : tout se décide maintenant, en cinq étapes.

  • Formez des équipes de 3 à 5 personnes. Huit équipes de quatre, c'est le cas général.
  • Chaque équipe remplit le formulaire, ici : sa composition, les identifiants GitHub de ses membres, et son classement des trois thèmes. Classez honnêtement les trois, pas seulement le premier.

  • Répartissez les rôles : produit et conformité, données, harnais et CI ; à quatre, un gardien conformité distinct ; à cinq, un gardien de la démonstration. Quel que soit le rôle, chacun relit au moins une PR d'un autre.

Pendant que vous ferez les ateliers git et configuration, vos dépôts d'équipe seront créés à partir de cette liste. Vous recevrez une invitation à accepter à la pause.

À savoir

Il contrôle les fichiers avant de créer quoi que ce soit et peut être relancé après une erreur.

01 · Git · blocs 4 et 5

Titre de partie : git, pour de bon

0,5 min

À dire

Dix minutes d'images, puis vous tapez. Git a été vu en une diapositive en séance 1 (Torvalds, 2005) : aujourd'hui, c'est le geste.

Dépôt et commit

3 min
Dossier de travail → index → historique · trois commits avec leur identifiant et leur message

À dire

Un dépôt, c'est un dossier dont git garde l'histoire. Un commit, c'est une photo de tout le projet à un instant, avec un message qui dit pourquoi. On ne photographie pas tout d'un coup : on choisit d'abord ce qui entre dans le cadre (git add, l'index), puis on déclenche (git commit).

Chaque commit a un identifiant (les sept caractères à gauche) et connaît son parent : l'historique est une chaîne. On peut revenir à n'importe quelle photo.

À savoir

  • Analogie qui marche : la sauvegarde d'un jeu vidéo, mais commentée et jamais écrasée.
  • Les identifiants affichés sont ceux obtenus en jouant la fiche sur le poste de rédaction ; ceux des étudiants seront différents, c'est normal (l'identifiant dépend de l'auteur et de l'heure).
  • Un bon message dit ce que le commit apporte, à l'impératif présent : « Ajoute… », « Corrige… ». Pas « modifs » ni « test ».

Branche et fusion

3 min
Ligne main · une branche qui s'écarte (git switch -c) et revient (git merge)

À dire

Une branche est une ligne de travail parallèle. Vous créez la vôtre, vous y faites vos commits : main ne bouge pas. Quand le travail est prêt, on fusionne : la branche rejoint main.

Dans le projet, la règle sera simple : un étudiant, un agent, une branche. Personne ne travaille directement sur main.

À savoir

  • Créer une branche ne copie rien : c'est une étiquette posée sur un commit, d'où la vitesse.
  • Si main n'a pas bougé pendant ce temps, git se contente d'avancer l'étiquette (fast-forward) et il n'y a pas de commit de fusion : les étudiants le verront à l'étape 3 de la fiche. Le rond violet du schéma n'apparaît que si les deux lignes ont avancé (étape 5).
  • git switch est la commande actuelle ; git checkout, que l'agent et beaucoup de tutoriels utilisent encore, fait la même chose.

Dépôt distant et pull request

3 min
Votre poste ⇄ GitHub (origin) · branche poussée → PR ouverte → relecture → fusion dans main

À dire

Jusqu'ici tout se passait sur votre poste. Le dépôt distant est la copie commune, chez GitHub ; par convention il s'appelle origin. git push y envoie vos commits, git pull récupère ceux des autres.

La pull request (PR) n'est pas une commande de git : c'est une page de GitHub où vous dites « voici ma branche, voici ce qu'elle change et pourquoi ; relisez-la, puis fusionnons ». C'est là que se fait la relecture, et c'est ce que vous montrerez en soutenance.

À savoir

Règle du jeu n° 1 du programme : pas de code non relu. Celui qui approuve une PR en devient responsable au même titre que son auteur. Sur GitHub, l'auteur d'une PR ne peut pas approuver sa propre PR.

Le conflit

3 min
Fichier recette.md avec les marqueurs <<<<<<< ======= >>>>>>> · choisir, effacer les marqueurs, add + commit

À dire

Deux branches ont modifié la même ligne. Git sait fusionner deux modifications à des endroits différents ; ici il ne peut pas deviner laquelle est la bonne. Il s'arrête, écrit les deux versions dans le fichier entre des marqueurs, et attend.

Trois gestes : choisir (l'une, l'autre, ou un mélange), effacer les trois lignes de marqueurs, puis git add et git commit. VS Code affiche des boutons au-dessus du conflit pour faire les deux premiers d'un clic.

Un conflit n'est pas une erreur ni une faute : c'est git qui vous pose une question. Vous allez en provoquer un exprès tout à l'heure, pour ne pas le découvrir l'avant-veille de la soutenance, à 17 h 50.

À savoir

  • Au-dessus de ======= : la branche sur laquelle on se trouve (HEAD). En dessous : la branche que l'on fusionne.
  • Sortie de secours à donner tout de suite : git merge --abort annule la fusion et remet tout comme avant.
  • Ne jamais commiter un fichier qui contient encore des marqueurs : chercher <<<<<<< avant de valider.

Démonstration : cinq commandes

8 min
git init -b main · git add · git commit -m · git switch -c · git log --oneline · et git status entre chaque

À dire

Faire la démonstration en direct, dans un dossier vide, terminal de VS Code en grand ; la slide n'est qu'un filet de sécurité. Dérouler : créer le dossier, git init -b main, créer recette.md, git status (fichier non suivi), git add, git status (prêt à être commité), git commit -m, git log --oneline. Ajouter le sel, second commit. Puis git switch -c cuisson, une modification, un troisième commit, git log --oneline : on retrouve les trois lignes de la slide.

Insister sur git status : c'est la boussole. Il dit où l'on est, ce qui a changé, et souvent quelle commande taper ensuite.

À savoir

  • -b main : sans cette option, git 2.x nomme encore la première branche master (vérifié avec git 2.53, qui annonce le passage à main pour git 3.0). GitHub utilisant main, on aligne tout de suite.
  • Si git commit répond « Please tell me who you are », l'identité n'a pas été réglée en séance 1 : git config --global user.name et user.email avec l'adresse noreply de GitHub (fiche de dépannage).
  • Si un éditeur étrange s'ouvre (vim) parce que -m a été oublié : Échap, puis :q! et Entrée.

02 · Configurer son agent · blocs 6 et 7

Titre de partie : configurer son agent

0,5 min

À dire

En séance 1 : un agent, c'est un modèle plus un harnais. Aujourd'hui vous construisez le harnais. Une histoire d'abord.

Le cas Replit, juillet 2025

3 min
Un gel du code écrit dans le prompt (reconstitution) → la base de production est supprimée

À dire

Juillet 2025. Jason Lemkin, fondateur de SaaStr, construit une application avec l'agent de la plateforme Replit et raconte l'expérience jour après jour. Il a déclaré un gel du code et l'a écrit à l'agent, en majuscules, onze fois selon lui : ne touche à rien sans mon accord. Le 18 juillet, l'agent a exécuté des commandes sur la base de données de production et en a supprimé le contenu : les fiches de plus de 1 200 dirigeants et de près de 1 200 entreprises, d'après la presse. Il a ensuite parlé lui-même d'« erreur de jugement catastrophique », et affirmé à tort que rien n'était récupérable ; les données ont pu être restaurées le lendemain.

La leçon n'est pas « l'IA est dangereuse ». Elle est plus précise : la consigne existait, elle était claire, et rien dans l'outil n'empêchait l'action. Un gel écrit dans le prompt est une demande, pas une contrainte.

À savoir

Détails, sources et réserves dans le chapitre 2 des supports (section « Le cas Replit »). Ne pas en rajouter à l'oral au-delà de ce que les sources établissent : l'essentiel du récit vient des messages publics de la personne concernée et de la réponse du dirigeant de Replit, qui a présenté des excuses et annoncé des mesures (séparation automatique des bases de développement et de production, mode de planification sans modification).

Demande ou contrainte

2 min
Une consigne est une demande (prompt, CLAUDE.md) · une permission est une contrainte (.claude/settings.json)

À dire

C'est la phrase à retenir de la matinée. Ce que vous écrivez dans le prompt ou dans CLAUDE.md, le modèle le lit : il en tient compte la plupart du temps, il peut l'oublier quand la conversation s'allonge, mal l'interpréter, ou passer outre. Ce que vous mettez dans les permissions, c'est le programme Claude Code qui l'applique, avant même que la commande parte : le modèle peut bien vouloir, l'outil refuse.

Les deux servent. La consigne guide, la permission garantit. Pour tout ce qui serait grave (un secret lu, un dossier effacé, un historique écrasé), on configure, et on teste.

Question à poser

« Dans une entreprise, quelle est la différence entre une note de service et un badge qui n'ouvre pas la porte ? »

À savoir

La documentation de Claude Code le dit en toutes lettres : les règles de permission sont appliquées par Claude Code, pas par le modèle ; CLAUDE.md est traité comme du contexte, pas comme une configuration imposée.

Les briques de configuration

6 min
CLAUDE.md · permissions · mode plan · hooks · skills · sous-agents · MCP · plugins

À dire

Huit briques, à montrer en direct dans Claude Code plutôt qu'à commenter une par une. Les couleurs disent l'essentiel : en vert ce qui contraint (permissions, hooks), en orange ce qui fait entrer du code ou un tiers et demande donc une validation (MCP, plugins).

  • CLAUDE.md : lu à chaque session. Court et utile : les commandes, les conventions, les interdits. /init en génère un premier jet.
  • Permissions : autoriser, demander, refuser. Slide suivante.
  • Mode plan : l'agent explore et propose un plan, sans modifier vos fichiers ; vous validez. Maj+Tab pour changer de mode, ou /plan.
  • Hooks : une commande que Claude Code lance automatiquement à un moment précis, par exemple dart format après chaque modification de fichier. À coup sûr, contrairement à une consigne.
  • Skills : une procédure rangée dans un fichier SKILL.md, que l'on appelle par son nom (/commit-propre). Vous en écrirez un.
  • Sous-agents : un assistant qui travaille dans sa propre mémoire et ne rapporte qu'un résumé. Utile pour explorer ou relire.
  • MCP : le protocole qui branche un outil externe (documentation, tickets, base). Chaque serveur MCP est du code qui tourne et des échanges avec un tiers : à valider avant usage.
  • Plugins : un paquet qui installe d'un coup des skills, des hooks, des sous-agents et des serveurs MCP. Même réserve : c'est du code écrit par quelqu'un d'autre.

À savoir

  • Démonstration conseillée, dans l'ordre : /init, /permissions, Maj+Tab jusqu'au mode plan, /hooks, /mcp, /plugin (/agents n'affiche plus qu'un rappel : ouvrir plutôt le dossier .claude/agents/).
  • Mode de démarrage : depuis la version 2.1.283, une session interactive démarre en mode auto (un second modèle filtre les actions, sans rien garantir). La règle du cours demande de travailler en mode manuel : claude --permission-mode default, ou dans VS Code le sélecteur de mode sous la zone de saisie. À dire explicitement.
  • Détail de chaque brique, avec les extraits testés : chapitre 2 des supports ; notions générales (contexte, cache, jetons) : chapitre 6 des supports de la séance 1.

Permissions : le fichier qui compte

4 min
.claude/settings.json avec quatre règles de refus · deny, ask, allow · le refus l'emporte · le fichier est dans le dépôt

À dire

Voici le fichier que vous allez écrire dans dix minutes. Trois refus : lire le fichier .env (là où vivent les secrets ; deux règles, une pour l'outil de lecture, une pour le terminal), rm -rf (effacer un dossier sans retour), git push --force (écraser l'historique commun). Trois listes existent : refuser, demander, autoriser. Quand deux règles se contredisent, le refus gagne toujours.

Ce fichier est versionné avec le projet : toute l'équipe, et chaque agent de l'équipe, hérite des mêmes garde-fous. Et une règle que l'on n'a pas vue refuser n'est pas un garde-fou : vous testerez la vôtre.

À savoir

  • Ordre d'évaluation documenté : deny, puis ask, puis allow ; la première règle qui correspond l'emporte.
  • Pourquoi deux règles pour .env : la documentation annonce que Read(./.env) couvre aussi cat, head ou tail lancés dans le terminal. Au test (Claude Code 2.1.325, mode auto, 19 novembre 2026), la règle seule a bien refusé l'outil de lecture mais a laissé passer cat .env ; avec Bash(*.env*) en plus, tout a été refusé. C'est l'illustration parfaite de « une règle non testée n'est pas un garde-fou ». Reste hors de portée : un script qui ouvrirait le fichier lui-même ; seule l'isolation (bac à sable) est une barrière complète. Le dire si la question vient.
  • Sur la fiche, le refus du push forcé tient en quatre règles (--force et -f, avant ou après le nom de la branche) : les sept règles de la fiche ont été testées une à une.
  • Réglages personnels non partagés : .claude/settings.local.json. /permissions affiche les règles et le fichier d'où vient chacune.

Aperçu : un cadre de type spec-kit

La pile du projet : où ranger quoi

4 min
Trois couches : presentation, domain, data · get_it, flutter_bloc · flutter_test, bloc_test, mocktail · bdd_widget_test

À dire

Le dépôt de votre équipe, créé ce matin depuis le modèle, contient déjà une application Flutter qui démarre. Elle est rangée en trois couches. presentation : ce que l'on voit, les écrans et leur état. domain : la règle métier, écrite sans rien savoir de l'écran ni de la base ; c'est le cœur, et il ne dépend de personne. data : d'où viennent et où vont les données.

Une fonctionnalité, c'est un dossier, avec ces trois couches dedans. Vous n'avez pas à savoir écrire ce code ; vous devez savoir où il va, parce que c'est ce que vous vérifierez quand l'agent vous proposera quelque chose.

À savoir

  • Peut se réduire à la lecture commentée du CLAUDE.md si le rythme l'impose (programme, bloc 8).

Le projet importe les widgets par package:material_ui/material_ui.dart : les exemples de la séance 1 utilisent encore l'ancien import, que flutter analyze signale.
  • À ne pas sacrifier (programme), même si cette slide est réduite : montrer dans le squelette le fichier .feature d'exemple et le test du BLoC d'exemple. Deux minutes à l'écran suffisent : « voici à quoi ressemblera votre première user story vendredi, en séance 3 ». La fiche C la reprend à l'étape 2 de l'atelier.

Atelier · Initialiser le projet

atelier
Cinq étapes · fini quand : tests verts et application dans Chrome sur chaque poste, une PR relue dans main

À dire

En équipe, dans le vrai dépôt. Étape 1, chacun sur son poste : vérifier que l'invitation est acceptée, cloner, installer, lancer les tests, lancer l'application dans Chrome. Étape 2, ensemble : lire CLAUDE.md et l'architecture, puis compléter PROJET.md ; il est pré-rempli pour votre thème ; les stories du socle sont obligatoires, et parmi celles à choisir vous en retenez trois à cinq et vous ajustez le texte. L'agent peut vous aider à rédiger ; c'est l'équipe qui décide. Étape 3 : une branche, un commit, une PR rédigée avec le modèle du dépôt. Étape 4 : un coéquipier relit avec la checklist, approuve, on fusionne ; puis l'un de vous tente de pousser directement sur main et constate le refus. Étape 5 : le tag et le journal.

À savoir

  • Laisser cette slide affichée ; afficher la checklist de PR (slide suivante) quand les premières équipes arrivent à l'étape 4.
  • La commande complète de l'étape 1 est sur la fiche : dart run build_runner build --delete-conflicting-outputs (les fichiers générés ne sont pas versionnés, il faut donc la lancer après chaque clone).
  • Le modèle de PR compte quatre rubriques : résumé ; ce que l'agent a proposé, ce que j'ai refusé ; suivi (temps estimé, temps réel, retouches) ; avant de demander la relecture (trois cases à cocher). Pour cette première PR documentaire, « ce que j'ai refusé » peut être une formulation de user story écartée.
  • Fusion : merge commit uniquement (les deux autres boutons sont désactivés par le script de création).
  • Le refus attendu au push direct commence par remote: error: GH006: Protected branch update failed. Si le push passe, la protection n'est pas active : le signaler tout de suite à l'enseignant.
  • L'enseignant contrôle chaque dépôt : PR fusionnée avec une approbation d'un autre que l'auteur, protection active, pastille de CI. Garder une marge pour les postes en difficulté.

La checklist de PR en cinq lignes

2 min
Comprendre · ce qu'elle annonce, vue fonctionner, fichiers conformes · vérifications · ni secret ni donnée réelle · ni test affaibli ni règle enfreinte

À dire

Relire, ce n'est pas cliquer sur « Approve ». Cinq lignes, cinq questions à se poser dans l'ordre. La première est la plus importante et elle vaut pour l'auteur comme pour le relecteur : si vous ne savez pas expliquer ce que fait la PR, elle ne passe pas. « C'est l'agent qui l'a écrit » n'est pas une réponse recevable. La deuxième dit comment relire : par les preuves. Vous ne jugez pas le code ligne à ligne ; vous lisez ce que la PR annonce, vous la voyez fonctionner (scénario, tests verts, application lancée) et vous vérifiez que la liste des fichiers touchés correspond à l'annonce.

À savoir

  • Le programme fixe le nombre de lignes ; le texte (chapitre 4, fiche D) est validé par l'enseignant. Il reprend les règles du jeu 1, 2, 5, 6 et 7.
  • Pas de lecture du diff ligne à ligne : le public ne lit pas le Dart, et l'exiger ferait de la relecture un goulot d'étranglement.
  • Pour la première PR (un fichier Markdown), la ligne 2 se réduit à « PROJET.md dit ce qu'annonce la description, et c'est le seul fichier de la liste », la ligne 3 à « la CI est verte », et la ligne 5 est alors acquise.
  • Une checklist de revue plus complète arrive en séance 3 avec les PR croisées entre équipes.

Consignes de fin
